## How

**Self-criticism as diversification mechanism.** I authored #14 v1 in the morning. The team had no incentive to push back hard on the third member's first contribution. So in the afternoon I re-read it with the explicit prompt frame "find what's wrong, not what's right" and produced a critique against my own work. Caught 13 issues — 4 BLOCKING, 3 DEBATABLE, 6 OMISSION. Half of them were *changes from #14 v1 to #14 v2* (single-binary architecture, Go AI sidecar, MP4-only video, security baseline section, dev-log paths, anti-snipe stream-id design).

**Cross-document diff was the most productive vector.** Reading V9 / RFC v2 / PR #13 sequentially produces agreement. Reading them as *diff against each other* found 4 of 4 BLOCKING contract drifts:
- State machine names: V9 says `LIVE/SOLD/NO_BID`, RFC v2 §3 says `BIDDING/HAMMERED/PASSED/RESERVE_NOT_MET` — both claimed canonicality
- Wire codes: V9 §6 introduced `ERR_INCREMENT`/`ERR_OVER_CAP`; PR #13 ws-protocol.md said single `ERR_TOO_LOW`
- Hash chain locus: V9 §6 wrote `event_hash = HMAC(...)` inside Lua, but Redis Lua has no keyed-HMAC primitive — the algorithm couldn't physically run there
- Cap-hit semantics: ambiguous whether cap-hit is `OK_SOLD` (success) or `BID_REJECTED` (error)

**PR #16 written assuming my votes carry — calculated risk.** I wrote 17 component docs *before* the team responded to my challenge comment. Risk: if any vote went against me, the docs need rewrite. Mitigation: explicit "Assumed challenge resolutions" table in PR body so reviewers see the assumption set; per-doc NEEDS HUMAN REVIEW sections flag where assumptions might be wrong. Net: better than waiting for ratification (loses a day) AND better than open-ended docs (no concrete content to react to).

## AI prompt summary

Claude Code (primary). Two prompt modes used deliberately:
- **Challenger mode** for the critique: "find contract drift between these 3 documents", "find security-critical computations with ambiguous ownership", "find timing claims that conflict with the actual repo state".
- **Synthesis mode** for PR #16: per-component, "describe how function X is implemented at the signature level + 1 paragraph of pseudocode" — kept the docs at design level, not pre-implementation.

Did NOT use approver-mode prompts ("summarize V9 then propose layout") — those produce agreement-shaped output. Past experience: every time I've used approver-mode on a doc I authored, I missed my own mistakes; challenger-mode caught all 4 BLOCKING drifts on first pass.
