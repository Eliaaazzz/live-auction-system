## What changed

1. **Hash chain** (`storedb.go`) — the Persistence Worker now fills `auction_events.event_hash`/`prev_hash` on the same Stream-first projection:
   `event_hash = HMAC-SHA256(key, prev_hash ‖ "\n" ‖ seq ‖ "\n" ‖ event_type ‖ "\n" ‖ payload)`, genesis `prev_hash=""`. Filled idempotently (`UPDATE … WHERE event_hash IS NULL`) so a crash between the INSERT and the fill self-heals on the next sweep. `VerifyEvidenceChain(aid) → (ok, hash_break_at_seq)` recomputes the chain.
   - **Key decision — hash over the MySQL-normalized payload.** JSON columns normalize key order/whitespace on store, so the read-back `payload_json` ≠ the original cjson bytes. The writer hashes the *read-back* form (same as the verifier reads), so both agree on one deployment. Documented in `proto/evidence-card.md §2`.
2. **Idempotent order** (`storedb.go` + `persistence.go`) — on `AUCTION_SOLD`, `CreateOrderFromSold` writes one `orders` row (UNIQUE(auction_id) + INSERT IGNORE + id derived from aid ⇒ exactly-once under re-projection / double worker). Done before the cursor advances → retried on failure.
3. **Evidence card v0** (`api.go handleEvidence`) — `GET /…/evidence` now returns the hash-chained `timeline`, the chain head `eventsHash`, a server-recompute `chainVerified` (+ `hashBreakAtSeq` on break), and the `order`. Additive; the only consumer (`web/room.html`) renders it verbatim.
4. **`verify-evidence` gate** — `lumen verify-evidence --auction <id>` (`RunVerifyEvidence`) exits ≠0 on `hash_break_at_seq`; `make verify-evidence`; wired into the CI `e2e` job (empty chain also passes ⇒ non-flaky).
5. **Config** — `EVIDENCE_HMAC_KEY` (env), non-default enforced outside `APP_ENV=dev` (§6); threaded through `store.New` so writer + verifier share the key.
6. **Contracts** — authored `proto/evidence-card.md` (`[全员 approve]`), updated `proto/db-schema.md`.

## Threat model (honest, §6)
Defends post-hoc single-point tampering of stored history (edit a payload/hash → chain breaks at that seq). **Not** external notarization; and since the HMAC key currently lives in process env (readable by the writer), this is an **integrity/consistency check**, not tamper-proof evidence — wording in `evidence-card.md §3`. KMS/separate-signer/rotation is post-MVP.
