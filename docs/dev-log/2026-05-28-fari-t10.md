## Load-gate false-green caught (#86 / #89 / #90)

The notable catch. @PDGGK's **#89** (recover the observer-WS panic + count it + add it as a load-gate breach `observer readErrors must be 0`) merged. His follow-up **#90** (`set -o pipefail` so `tee` stops swallowing the load-harness exit code) came in APPROVED but with a **red e2e**. Digging into the failure rather than the checkmark:

```
observer: frames=6764 readErrors=6
load: load FAIL: observer readErrors=6 (must be 0)
make load-smoke: FAIL (rc=1)
```

So: **main is currently false-green on load-smoke** — the readErrors breach (added by #89) fires deterministically, but `tee` masks the exit code, so the e2e job stays green. #90 correctly unmasks it; merging #90 would (rightly) red main until the breach is 0. @PDGGK independently reached the same conclusion and we both held #90.

Root-caused the breach (posted on #86): `runObserver` counts any non-timeout read error while `ctx` isn't yet cancelled, and `isTimeout` only exempts close codes 1005/1006 — so connection-teardown reads (normal-close 1000/1001, "use of closed network connection") get counted. Proposed: log the actual close codes first, then exempt benign teardown closes so `readErrors must be 0` measures real mid-run frame loss. Deferred the verify to PDGGK (he has the Docker repro; I don't). **#90 stays blocked on #86.**
