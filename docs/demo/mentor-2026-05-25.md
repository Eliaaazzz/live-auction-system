| "Why Redis Lua instead of an RDBMS transaction for the bid hot path?" | Per [`docs/architecture.md` §6](https://github.com/Eliaaazzz/live-auction-system/blob/main/docs/architecture.md) + V9 §4.2: bid p95 < 80ms gate + 500/50 sustained means the hot path cannot afford a network round-trip + row-lock contention per bid. Redis-Lua runs adjudication atomically (single-threaded execution, no isolation cost), with the Stream as the **durable** log (append-only, gap-free `<seq>-0` IDs) and MySQL as the projected **fact** store via the persistence worker. Lua holds *no* mutable state itself; correctness lives in the Stream. ACID semantics are recovered at the projection layer (INSERT IGNORE on UNIQUE(auction_id, seq) + replay verifier). T6 ships the 3-way diff; T4 ships the HMAC hash chain so tamper detection is cryptographic, not procedural. |
| "AOF everysec — what does that actually guarantee, and what's the worst-case loss?" | Per [`docs/decisions.md` §AOF](https://github.com/Eliaaazzz/live-auction-system/blob/main/docs/decisions.md): we run Redis with `appendonly yes` + `appendfsync everysec`. Worst case = **1 second of accepted bids lost** on hard kernel panic between fsyncs. We bound that with: (a) the **persistence worker projects every Stream event into MySQL within ~2s** (the sweep cadence) so the durable fact-store catches up; (b) the **Replay Verifier** (T6) compares Stream vs MySQL post-incident to detect any divergence; (c) the **HMAC hash chain** (T4) makes any silent backfill detectable. We don't run `appendfsync always` because that adds ~5ms per bid — would breach the §4.2 ack p95 < 80ms gate. |
| "Safety, abuse, and compliance — what's in place?" | Per [`docs/charter.md`](https://github.com/Eliaaazzz/live-auction-system/blob/main/docs/charter.md) + V9 §8: (1) JWT on every WS frame, dev-login flag disabled in non-`dev` env (server fails to start if `ENABLE_DEV_LOGIN=true` and `APP_ENV!=dev`); (2) seller cannot bid on own auction (`place_bid.lua` checks `sellerId` from state Hash); (3) `Origin` allowlist on WS upgrade; (4) `MaxMoneyCents = 2^53-1` enforced at REST + Lua to bound float64 precision; (5) `MaxExtensions` cap bounds anti-snipe to prevent runaway endAtMs; (6) AI sidecar uses Doubao with a documented prompt template + ban-words filter; AI outputs are non-authoritative (bid path doesn't trust AI). Compliance gaps: no human content review queue for image uploads, no auctioneer audio retention policy — both flagged in V9 §8 as P2. |
| "Map the 50/25/15/10 rubric to what you've actually shipped vs deferred" | Per `docs/charter.md` scoring → V9 §10 timeline: **50% architecture + Q1-Q9** = shipped (PR #13 SoT, PR #21 v4 diagrams, PR #16 17 component docs, decisions.md with Q1-Q9 rationale). **25% production-ready code** = T1 wire ✓ + T2 atomic bid core 🟡 (in CR), T3 hammer 🟡 (just opened), T4-T7 scheduled. **15% observability** = scaffold ready (PR #18 in CR; design docs in PR #16 component 13); live dashboards activate when PR #18 merges + `/metrics` handler lands. **10% chaos + evidence** = PR #24 AI drill wired end-to-end, 4 invariants implemented + unit-tested (live-drill artifact pending); 4 other phases stubbed with specs.
