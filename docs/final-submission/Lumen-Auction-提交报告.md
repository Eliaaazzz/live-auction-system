## 四、核心功能清单

我们按用户路径将系统能力归纳为五个功能群。前两个面向真实用户（商家与买家），构成赛题要求的核心闭环；后三个属于工程能力与演示能力，是本作品区别于一般竞拍 Demo 的关键所在。

### 4.1　商家 / 主播端（PC 管理后台）

商家在管理后台完成从上架到成交的全部运营动作。上架环节支持填写商品标题、图片地址与介绍，并由 AI 视觉模型抽取一份商品事实草稿，商家逐项确认后方可进入后续流程。规则配置覆盖起拍价、加价幅度、封顶价、拍卖时长、反狙击延时窗口与最大延时次数，并可选择七种竞拍模式之一。直播控制台将一场拍卖的生命周期清晰地表达为「草稿 → 冻结规则 → 开拍 → 实时出价 → 一键取消 → 落锤 → 订单」的状态流转。成交后系统自动生成订单，商家可在订单管理中查阅成交详情，并下载带哈希链的证据文件以备审计。

### 4.2　买家端（移动 H5）

买家端是竞价氛围的主舞台。直播间在生产环境播放火山直播 HLS 流，在网络不可用时退化为本地模拟画面，并通过房间级 WebSocket 长连接保持与服务端的毫秒级同步。出价采用「HTTP 优先、WebSocket 兜底」的双通道设计，两条通道共用同一去重标识，确保任意一条通道可用即可完成毫秒级出价确认。

在氛围层面，系统实现了领先与被超越的即时闪烁反馈（对应赛题加分项「🎉 领先！」与「⚡ 被超越！」的情绪反馈）、价格翻滚动画、排行榜头像飞行动画（对应「实时排行榜」）、末十秒红圈脉冲与心跳音（对应「倒计时动画与出价提示音」的紧张感营造）、反狙击延时的光带横扫以及落锤后的荣耀时刻特效。我们尤其重视让「规则被看见」：当反狙击延时触发时，界面会以显式横幅告知「反狙击触发 · 延时 +30s · 第 3 次」，而非让倒计时悄然变长；当用户被超越时，行动号召按钮会直接给出「再加 ¥5,000 反超」这样的具体动作；长按出价按钮则会弹出加价轮盘，与点击走同一条出价通道。断线后系统自动重连，并以最后接收序号为锚点补放遗漏事件，保证用户视角的连续。

**语音出价（确认式）**：买家端集成了一条基于浏览器 SpeechRecognition 的语音出价通道（`apps/web/src/components/VoiceBidButton.jsx`、`apps/web/src/lib/voicebid.js`）。买家可以直接对手机喊出「加价五千」「出价十三万八」「加一手」等中文短语，前端将其解析为字符串分单位的目标金额，呈现为一行确认信息，**仅当买家显式点击确认按钮后**才走与点击轮盘完全相同的出价通道（共享同一客户端出价标识、共用 HTTP 优先 + WebSocket 兜底）。不支持语音 API 的浏览器与识别异常会降级为可见提示而不阻塞普通出价；当前价或加价幅度在确认前发生变化，待确认的语音金额会被主动清除，避免买家提交过期解析。这一设计把 AI 能力延伸到买家侧，又通过「显式确认」严格回避了「AI 替用户决定金额」的合规风险。

### 4.3　AI 旁路（Doubao-Seed-2.0-lite）

AI 能力以独立旁路的形式接入。视觉模型负责从商品图中抽取品牌、型号、成色、瑕疵等结构化事实草稿，这些草稿不会自动写入数据库，必须由商家逐项确认后才能进入正式拍卖；语言模型则在开场、跳价、冷场与落锤四个触发点生成拍卖师话术，逐字流式呈现。AI 旁路在离线时降级为一个状态徽标，对出价路径不产生任何阻塞。

### 4.4　七种竞拍模式

赛题要求的五条规则（0 元起拍、加价幅度、封顶价、自动延时、异常取消）已全部实现；在此之上，我们引入六种额外的定价与对抗模式，全部由统一的策略注册表派发。七种模式覆盖：英式（公开升价基线）、突然死亡（过点即落锤）、一价密封（首价密封拍）、二价密封（维克里）、混合揭示（藏领头羊、露次席）、全员付费（演示性虚拟币罚没）与两阶段预选（密封预热加正式开拍）。每种模式都有独立的 Lua 脚本与严格断言的演示，并全部纳入持续集成回归网；其中全员付费模式以「虚拟币 · 非真实支付 · 非赌博」标识严格界定其合规边界。各模式的经济学原型与关键技术实现详见第十三章亮点一。

### 4.5　工程门禁与可观测性

系统内置回放校验器，对 Redis 事件流、Redis 状态快照与 MySQL 投影三方逐序号比对，输出「一致 / 在某序号失配 / 哈希在某序号断裂」三类机读结论；每一条拍卖事件都参与 HMAC SHA-256 链式哈希，任意一行被篡改都会在校验时立即暴露。系统同时暴露指标接口与版本接口：前者用于观测出价确认时延、广播时延、序号空洞与在线连接数；后者返回协议版本（`schemaVersion=2`）、构建提交号（`buildSha`）、构建时间（`buildTime`）与运行环境（`appEnv`）四个字段，持续交付流水线在部署后以「协议版本等于 2、构建号等于期望提交号、构建时间不为 unknown」三项条件强校验，任何漂移立即视为部署未生效。这样便从机制上保证「演示时所看到的线上系统，正是持续集成验证通过的那个二进制」。在异常告警方向，背压强制关闭数、序号空洞数、AI 离线时长与回放校验失败等关键信号均已通过指标接口暴露，可由外部 Prometheus 与 Alertmanager 拉取并按阈值触发；演示期间我们以人工巡视指标接口替代实际告警通路的接入，并将告警通路的正式接入列为部署后续工作。

## 五、端到端使用流程

一场完整拍卖从商家登录到演示后回放，可由以下八步连贯完成。

1. **登录**：商家访问管理后台并通过登录接口取得卖家身份（生产环境关闭开发态免登录）；买家直接进入首页浏览公开拍卖列表。
2. **发布**：商家在「新建拍品」页填写标题、图片地址与介绍，视觉模型自动抽取若干条事实草稿，商家逐项确认后配置规则（含模式选择），提交后得到一场处于草稿态的拍卖。
3. **开拍**：商家先「冻结规则」使拍卖进入已排期态，再点击「开拍」使其进入直播态，状态机由此进入实时阶段。
4. **观看与出价**：买家进入直播间后 WebSocket 自动建连并拉取首屏快照；点击加价按钮（或对手机喊出「加价五千」并确认）经 HTTP 命令通道（或 WebSocket 兜底）抵达后端，由 Redis Lua 脚本原子裁决，随后在同一连接上直接确认并向房间广播。
5. **氛围与反狙**：当前价翻滚、排行榜飞行、领先时金色闪烁与心跳音、被超越时红色掉落条与反超号召、末十秒红圈脉冲；在反狙击窗口内出价会触发延时事件与光带横扫。
6. **落锤**：定时工作进程检测到结束时刻到期，调用落锤脚本原子裁决，发布「成交 / 流拍 / 取消」三种终态之一，前端随即播放落锤音与结果页。
7. **支付与证据**：成交后持久化进程以拍卖唯一约束幂等创建订单，买家完成模拟支付；点击「查看证据」即可看到每个事件的序号、类型与前后哈希构成的链条。
8. **演示后回放**：运营可在任意时刻对该场拍卖运行回放校验与证据校验，确认三方数据一致且哈希链未被篡改。

## 十、系统架构图

系统遵循「客户端 — 接入层 — 核心层 — 数据层」四层架构，AI 能力以外部旁路形式接入。客户端包含 PC 管理后台、移动直播间与压测机器人；接入层由 Caddy 负责 TLS 终止与 WebSocket 升级，向后分流至承担鉴权与命令路由的 REST 后端与承担房间隔离与广播的 WebSocket 网关；核心层汇聚拍卖服务、出价引擎、定时落锤、订单服务、持久化进程与回放校验，全部写操作以 Redis Lua 脚本为唯一入口；数据层以 Redis 7 作为实时热源、MySQL 8 作为持久化事实库。

*图 10-1　Lumen Auction 系统架构总览（四层 + 外部服务，见 docx 附图）*

一次出价的关键调用链可概括为：浏览器以 HTTP 优先方式向出价接口发起请求，服务端将其交给 Redis Lua 脚本完成原子裁决——脚本在单线程内连续完成状态校验、金额与封顶校验、反狙延时判定、序号自增、事件追加与房间发布，随后服务端在同一连接上直接返回出价确认；广播则由订阅协程消费发布通道后向房间内所有连接扇出，在万人房间下以合并广播降低写放大。外部服务方面，AI 旁路进程经 HTTP 单向触发调用 Doubao 模型，核心从不等待 AI 结果，超时即降级。

### 10.1　数据采集与治理

对照赛题对「从竞拍数据采集、数据治理到后端服务」完整链路的要求，本系统的数据链路可逐段复核。采集侧，所有出价命令经 REST 命令通道或 WebSocket 入口进入服务端，连接、断线、重连与出价频次等用户行为经指标接口聚合为可观测序列。治理侧，每一笔拍卖事件由 Redis Stream 作为权威账本完整留痕，每条事件含序号、事件类型、负载、前序哈希与本条哈希五个字段，并由持久化进程投影至 MySQL 长期保存，形成「实时账本 + 长期事实库」的双层留存。AI 调用侧，系统在 MySQL 中维护 `ai_usage_logs` 表，按场景、模型、输入摘要、输出摘要、是否人工评审与最终决策（采纳 / 修改 / 否决）等字段长期归档每一次有意义的调用，构成「AI 行为可追溯」的数据治理基础。这样，从出价与行为的采集、到事件账本与投影的留存、再到 AI 调用的归档，整条数据链路都可被逐条复核。

### 10.2　技术选型与场景适配

选型层面，本团队的每一项决策都服务于「实时、原子、可裁决」三个目标。后端选择 Go 而非 Node.js，是因为 goroutine 模型天然契合「每条 WebSocket 连接对应一个轻量并发单元」的网关需求，单进程即可把万级连接的扇出做出可预期的尾延迟；同时 Go 的单一静态二进制产物部署门槛低、构建可重现，与「演示即验证过的二进制」目标相互成全。出价裁决选择 Redis 单线程加 Lua 单脚本而非分布式锁，是因为分布式锁需要租约、续约与时钟假设，复杂度高且对时钟漂移敏感，而 Redis 的单线程串行特性可将「读状态、校验、写状态、发布」打包为一次原子操作，让复杂度与正确性同时达到最优。我们也刻意没有引入 Socket.io 等高层抽象库——这类库往往把协议版本、背压控制等关键边界隐藏在框架内部，而本系统恰恰需要这些边界对契约文件可见、对持续集成可测、对评委可示；原生 WebSocket 加自研协议层（协议版本、最后序号补放、带类型关闭码）反而是更可控的选择。

前端选择 React 与 TypeScript，一方面借助成熟的组件测试生态同时服务于氛围动效与单元覆盖两个目标，另一方面以 TypeScript 在 WebSocket 信封、状态机与金额字符串等跨模块契约上提供编译期保护，与 proto 契约文件共同构成「编译期加运行时」的双重一致性。数据层将 Redis 7 用作实时热源与事件账本、MySQL 8 用作长期事实库与投影，二者职责分离规避了「以同一套存储既做实时交易又做长期分析」的常见陷阱；且 Redis Stream 的「序号-0」式标识可直接映射到 MySQL 中「拍卖号加序号」的唯一约束，使两层数据在结构上天然对齐。

## 十一、大模型 / AI 能力使用说明

### 11.1　模型与服务

系统统一使用字节火山方舟提供的 Doubao-Seed-2.0-lite 一体化多模态模型：其视觉能力用于商品图事实抽取，语言能力用于拍卖师话术生成。出于「一个课题所有成员共用账号、不外泄、仅用于本课题」的资源使用要求，模型接入点与密钥仅以环境变量形式注入运行环境，不在仓库与本报告中登载。

关于「开源模型调用（可选）」一项的取舍：本系统将 AI 调用定位为「非裁决、毫秒级失败可降级」的旁路接入，因此对模型托管与调度复杂度有意做减法。Doubao 一体化多模态服务以单一接入点同时覆盖视觉与语言两类需求，符合「赛事方推荐资源、一体化调用、失败可降级」三项条件，本团队评估后认为没有引入开源模型并自建本地推理服务的必要——这一选择本身即体现了「AI 仅做旁路、不做权威」的工程取舍。

### 11.2　AI 在系统中的位置与边界

AI 旁路是一个完全独立的进程（独立容器、独立部署），与核心服务之间仅通过 HTTP 单向调用通信。我们将「AI 永不参与裁决」确立为系统的一条硬不变量。

AI 调用的超时实际上是一条**多层防线**，每一层都设有硬上限以保证核心永不等待：

- **网关 → 旁路（lumen→sidecar）**：每次 HTTP 调用的客户端层 5 秒硬超时（`apps/lumen/internal/server/auctioneer.go`），与 `proto/ai-events.md` 中的契约声明一致。这是出价/状态/订单路径相对 AI 旁路的最大耐心。
- **旁路 → Doubao 模型**：默认 30 秒，可通过环境变量（如 `LLM_TIMEOUT_MS`）覆盖；同步上游推理可能较慢的真实模型路径，在 issue #253 中由 8 秒上调（`apps/ai-sidecar/internal/llm/openai.go`）。
- **图片抓取**：旁路侧 5 秒硬超时（`apps/ai-sidecar/internal/ssrf/allowlist.go`），同时受 SSRF 白名单约束。

任何一层超时都立即触发降级：HTTP 调用失败 → 旁路返回兜底文案 / 界面徽标；网关侧 5 秒超时 → 界面徽标；出价、状态机与订单路径**完全不受影响**。运维侧的目标是让首字时延的中位数控制在数百毫秒内，这取决于 Doubao 服务端的实际响应，并非配置门限。这一多层边界保证了无论模型是否可用、响应快慢如何，竞拍的正确性与实时性都不会动摇。

### 11.4　视觉事实抽取的产品边界

商家上传商品图后，视觉模型按提示抽取若干条结构化事实（品牌、型号、成色、关键参数、瑕疵等；提示模板的目标为五到八条，实际条数视模型输出而定）。这些事实并不会自动写入数据库，商家须在后台逐项确认、编辑或删除，全部确认后该拍卖才能由已排期态进入直播态。我们以此划定 AI 落地的产品边界：AI 用于提效，但不替代卖家对商品描述真实性的责任。

### 11.5　AI 离线降级（硬不变量）

「AI 离线时拍卖核心百分之百不受影响」是一条写入持续集成门禁的硬约束。验证方式是在持续集成中停掉 AI 旁路容器后重跑端到端出价用例（必须通过），再重启旁路后复跑一次（必须通过），任意一次失败都会导致合并被拒。界面表现为 AI 气泡顶部出现「拍卖师暂离」徽标，出价、倒计时与排行榜不受任何阻塞。

### 11.6　AI 编码工具的使用与代码贡献率

在工程过程中，本团队主要使用 Claude Code 与 Codex 两款 AI 编码工具辅助开发。选择这两款工具，是基于它们与本课题工作流的适配：Claude Code 擅长仓库级、多文件的上下文推理，能依据我们以契约文件落盘的接口规范执行跨模块改动，契合「契约先行」的协作纪律；Codex 在快速生成脚手架、测试夹具与重复样板代码上效率突出，适合承担界面与测试层的起草工作。两者均以命令行与代理式工作流运行，天然嵌入「合并请求评审加四道持续集成门禁」的流程，使 AI 起草的产物必须经人工评审方能合入。需要说明的是，本报告并不主张这两款工具是赛事唯一推荐或最优的选择，只陈述本团队基于自身工作流所作的取舍；我们也没有选用 GitHub Copilot 等单文件级补全工具，原因是本作品对「跨模块契约一致性」的要求高于「单行补全速度」，更适合具备整仓库视野的代理式编码工具。我们在仓库内以日志模板逐条记录有意义的 AI 起草决策，确保使用流程规范、可追溯。

就贡献率而言，我们的自评是：核心业务代码（出价裁决、状态机、Lua 脚本、回放校验）约三到四成由 AI 起草、人工驱动并经严格评审；界面与脚手架代码约六到七成；测试与文档约五成。需要说明估算口径：上述比例由 git blame 行级统计与评审记录中「AI 起草、人工修改 / 否决」标签交叉粗估而来，且以「AI 起草、人工把控」（人工合规修改加显式批准）为准，并不把行数膨胀本身当作指标。

我们认同「AI 代码贡献率并非越高越好，关键在于关键决策点的人工把控」这一判断，并据此组织整个工程纪律。具体而言，关键决策点百分之百由人工设计，AI 仅协助补全细节代码。例如：出价 Lua 脚本的原子边界——读状态、校验、去重、计算新序号、写状态与发布的六步顺序及其失败语义——由人工设计，AI 仅协助生成边界检查的细节实现；HMAC 哈希链的密钥威胁模型边界——「校验者与写入者同进程时降级为内部一致性保证」这一安全口径——完全由人工评估并写入安全基线文档；七种竞拍模式的派发架构——以策略注册表统一收口、各模式只实现差异化裁决——由人工经设计评审决定，AI 协助生成各模式 Lua 脚本骨架后再由人工逐条校核不变量。所有 AI 起草的代码都必须经过合并请求评审与四道持续集成门禁方能合入。此外，系统在 MySQL 中维护 `ai_usage_logs` 表，按场景、模型、输入摘要、输出摘要、是否人工评审与决策（采纳 / 修改 / 否决）等字段长期归档每一次有意义的 AI 调用，与「契约先行、全员批准」纪律共同构成 AI 使用的可审计基础。

## 十二、关键工程难点与解决方案

竞拍系统的工程难度集中在「高并发下的正确性」与「实时性下的一致性」两条主线上。本章选取五个最具代表性的难点，逐一说明问题本质、解决方案与验证结果。这五个难点合在一起，覆盖了评分标准中「出价校验与状态机管控」「系统可用性与异常兜底」「性能、稳定性与数据一致性」「可观测性」等几乎全部考察要点。

### 12.1　难点一：高并发出价的原子性与防双花

当上百名用户在最后一秒同时狂点出价按钮时，系统必须同时保证四件事：同一笔出价（以客户端出价标识为准）不能产生两条记账；事件序号严格单调递增且无间隙；卖家自拍、封顶价、反狙延时窗的判定必须原子完成；任何失败都要返回明确的错误码，使前端能直接据此给出交互反馈。任何一处出现竞态，都可能导致「一笔出价扣两次钱」或「排名错乱」这类不可接受的后果。

我们的方案是将 Redis Lua 脚本作为唯一的写入入口。Go 层的所有出价路径都只调用 Lua，不存在绕开脚本直接写状态的可能。由于 Redis 单线程执行、整段 Lua 天然串行，我们无需引入分布式锁或事务即可获得原子性。脚本逻辑可概括为下列六步。

```text
-- place_bid.lua（逻辑简述）
1. 读取状态 Hash（status / current / seq / sellerId / endAtMs）
2. 校验：直播态、非卖家自拍、金额 >= 当前价 + 加价幅度、未超封顶、未过期
3. 去重：命中此前缓存的 clientBidId 则直接重放原确认（幂等）
4. 计算新价、新序号，并按反狙规则计算可能的延时
5. 写状态 Hash + 写排行榜 ZSET + 追加事件 Stream + 发布房间频道
6. 返回 JSON 编码的出价确认载荷
```

这一设计带来几个关键性质：整段裁决无锁原子执行；事件流的标识被设计为「序号-0」，使序号与流偏移严格一一对应，后续断线补放可直接用区间查询切片喂给客户端而无需额外排序；多键操作通过哈希标签固定在同一槽位，为将来切换到 Redis 集群预留了空间。在万级并发的压测中，出价确认时延的 95 分位为亚毫秒级，序号空洞为零，背压强制关闭为零，回放校验结论为一致，哈希链校验通过。具体数字见第十四章。

### 12.2　难点二：状态机的七个规范状态与八条不变量

竞拍的生命周期天然复杂，从草稿、已排期、直播，分叉到成交、流拍、取消，再到订单创建，过渡条件、可见性与前端渲染都必须严丝合缝。一个常见的陷阱是把「自动延时」误当作一个独立状态——它实际上只是一个事件，状态并不改变。若处理不当，前端就会出现状态与事件混淆的渲染错误。

我们的处理是把生命周期明确收敛为七个规范状态，并写入状态机契约：草稿、已排期、直播、成交、流拍、取消、订单已创建；「自动延时」被强制定义为事件而非状态，前端将其渲染为延时计数徽标与光带动画。所有状态转移都由 Lua 单点强制：开拍、出价、落锤、取消各由独立脚本负责一段过渡，Go 层不会绕开。在此之上，我们将八条不变量写入评审准则，作为每一次代码评审的检查清单。

| 编号 | 不变量 | 强制点 |
|---|---|---|
| P1 | 金额跨边界一律以字符串十进制传递，不使用浮点数 | 后端定点分单位 + 前端大整数 |
| P2 | 七个规范状态与界面严格一一映射 | 前端单一状态徽标映射表 |
| P3 | AI 永不参与裁决 | AI 离线端到端门禁 |
| P4 | 倒计时以服务端时钟为准 | 客户端维护时钟偏移 |
| P5 | 延时计数在界面必须可见 | 延时徽标强约束 |
| P6 | 证据链 HMAC SHA-256 完整 | 证据校验退出码 |
| P7 | 断线以最后序号补放 | 补放协议 + 快进动画 |
| P8 | WebSocket 处理不阻塞广播 | 性能冒烟持续监测 |

### 12.3　难点三：WebSocket 的不稳定性与万人房间的广播压力

两类压力在此交汇。其一是连接的不稳定：用户网络抖动、NAT 超时、手机熄屏都会导致长连接中断，系统必须能恢复且不丢事件。其二是广播的写放大：单房间上千用户时，一次出价确认要扇出给所有人，朴素实现会让广播写入成为瓶颈。赛题加分项给出单房间千人在线的基线，我们将目标提高到一万用户，即该基线的十倍。

针对连接恢复，每个客户端在重新加入房间时携带自己最后接收到的序号，服务端以区间查询补齐缺失事件，缺口过大时则直接下发一份全量快照。针对广播写放大，我们设计了大房间合并广播：当房间观众数超过阈值时，将连续的出价确认合并为单帧状态补丁，按固定频率刷新；与此同时，出价者本人仍由其所在连接直接收到毫秒级确认，其余观众降级到合并补丁。这一设计把广播的写放大因子从「每秒出价频率乘以房间人数」降为「补丁刷新频率乘以房间人数」——前者随出价突发而线性增长、不可控，后者则由服务端配置的刷新上限封顶，从而使万人房间的广播时延 99 分位稳定在数百毫秒以内。

在背压治理上，我们将下行帧分为关键与尽力两类双车道：关键帧（出价确认、终态事件、快照、补放）若缓冲溢出则以带类型的关闭码强制断开，客户端据此反弹重连并补放；尽力帧（心跳等可重发内容）溢出则仅丢单帧而保留连接。我们还进一步把确认与广播拆为子通道，确保出价者本人的确认永远不会被房间广播堵塞。心跳保活防止操作系统级的长阻塞读，协议版本门禁则让客户端能区分「协议不匹配」与「网络故障」两类降级路径。

### 12.4　难点四：可裁决与可回放的财务级审计

竞拍属于资金类业务，仅做到「实时一致」并不足够，还要能够事后回放、能查篡改、能向客户或监管说明「为什么是这个人赢」。为此我们建立了「三方一致回放校验 + HMAC SHA-256 哈希链」的审计能力。三方数据源分别是作为权威账本的 Redis 事件流、便于查询的 Redis 状态快照，以及持久可备份的 MySQL 投影。回放校验器从事件流起点重放全部事件，在序号层面比对三方是否一致，输出机读结论。哈希链则对每一条事件按下式逐链计算。

```text
event_hash = lowerhex( HMAC_SHA256( KEY,  prev_hash || seq || event_type || payload_json ) )
```

篡改任意一行都会导致其后所有哈希断链，证据校验立即报出断裂序号。客户端的证据卡将每个事件的序号、类型与前后哈希前缀直观呈现，可展开查看完整链条。我们同时公开声明本方案的威胁模型边界：由于哈希密钥与写入者同进程，内部攻击者理论上可以重链伪造，因此这是一种「内部一致性检查」而非「对外不可伪造证明」；要做到后者需引入密钥管理服务与独立签名服务，这一点已列入后续安全基线规划。我们认为，明确声明边界比夸大其词更符合工程诚信，也正中评分维度对「数据一致性与可观测性」的考察。

### 12.5　难点五：部署稳定性与「演示即验证过的二进制」

演示当天最怕的情形是「部署的是过期分支」——持续集成全绿，但 ECS 上跑的却是上周的二进制。我们曾在一次北京万级测试中被新旧协议版本不匹配打断，因而把「部署身份」上升为一等工程问题。解决方案由四部分组成：版本接口返回协议版本、构建标识、构建时间与运行环境；持续交付流水线在部署后以版本接口的构建标识与期望值强校验，校验失败即视为部署未生效；另有部署前的预检脚本执行同样的校验逻辑作为干跑门禁；上传采用分块加哈希校验，避免网络抖动下「半上传半失败」的尴尬状态。这套机制让评委可以通过访问版本接口，一眼确认线上系统的新鲜度与真实性。

## 十三、项目亮点与创新点

遵循导师「把一个亮点做到极致，胜过十个浅尝辄止」的提示，我们将差异化集中在三处：产品想象力上的七种竞拍机制、工程严谨度上的可裁决可回放、以及高并发与 AI 旁路的工程纪律。

### 13.1　亮点一：从英式拍卖到七种竞拍机制

赛题要求的五条规则我们全部实现，但仅此尚不足以形成差异化。我们回到「竞拍即动态定价」这一本质，在英式公开升价之外引入六种额外机制，全部由统一的策略注册表派发，每种模式都有独立的 Lua 脚本与严格断言的演示，并全部纳入持续集成回归网。

| 模式 | 经济学原型 | 关键技术实现 |
|---|---|---|
| 英式 | 公开升价（赛题基线模式） | 反狙延时 + 公开排行榜 |
| 突然死亡 | 过点即落锤 | 规则归一化时自动清零延时窗 |
| 一价密封 | 首价密封拍 | 直播期间不下发出价金额，落锤时一次性揭示 |
| 二价密封 | 维克里拍卖 | 同密封路径，落锤时按第二高价成交 |
| 混合揭示 | 半隐藏：藏领头羊、露次席 | 排行榜与广播均对当前领先者做服务端过滤 |
| 全员付费 | 美元拍卖 | 次席罚没虚拟币、不生成真实订单，界面强制显示合规标识 |
| 两阶段预选 | 密封预热 → 形成底价 → 英式高潮 | 派生正式场接口 + 底价推荐启发式 |

*表 13-1　七种竞拍模式与其经济学原型*

这一组模式之所以构成亮点，在于它来自对赛题本质的产品深化，而非对题面的简单复制。其中全员付费模式涉及合规风险，我们将其严格限定为演示性虚拟币机制，并由戴子涵起草、全员批准，要求界面以中文为主、英文为辅强制显示「虚拟币 · 非真实支付 · 非赌博」标识。合规边界的清晰兑现，本身也是评分加分项的真实落地。

### 13.2　亮点二：可裁决与可回放的财务级正确性

我们追求的并不止于「能展示一个炫酷的 Demo」，而是「能向裁判证明上一场拍卖的每一笔出价为何生效、谁在何时以多少金额胜出、记录有没有被改过」。如第十二章所述，三方一致回放校验与 HMAC 哈希链共同构成这一能力，客户端证据卡使其对评委可见，而对威胁模型边界的公开声明则让这份「证明」立得住、经得起追问。我们刻意区分「内部一致性检查」与「对外不可伪造证明」，并把后者明确归为引入密钥管理服务与独立签名服务的后续工作；对自身能力边界保持工程诚实，而不是用「区块链」之类的热词去包装一个内部哈希链，本身即是这套审计设计的差异化所在。这一项直接命中评分维度中的「系统可用性、数据一致性与可观测性」。

### 13.3　亮点三：高并发硬核与 AI 旁路的工程纪律

在高并发方向，系统在单房间达到一万 WebSocket 连接。需要说明口径：赛题挑战二的基础要求是「百人以上同时狂点出价按钮」，加分项进一步给出「单直播间千人以上同时在线」的基线；本作品以加分项基线（千人）为对照，单房间实测一万连接，达到该基线的十倍。在此之上，大房间合并广播把广播写放大从随出价突发线性增长收敛为由补丁刷新频率封顶；双车道背压与带类型关闭码保证慢客户端不拖累整个房间；HTTP 优先与 WebSocket 兜底的双通道让出价确认走最快路径。跨端状态同步层面，HTTP 命令通道与 WebSocket 兜底通道共用同一客户端出价标识，配合断线后以最后序号补放、协议版本门禁，使「网页、手机、重连、协议升级」四类同步场景都在同一契约下统一兜底。在 AI 方向，旁路百分之百不参与裁决、视觉事实须经卖家确认才进入核心、拍卖师离线降级为徽标、AI 离线端到端在持续集成中受强约束、编码使用日志全程可追溯；买家侧的语音出价进一步把 AI 能力向需求侧延伸，但严格通过「显式确认」回避「AI 替用户决定金额」的合规风险。在工程纪律方向，我们沉淀了二十五份以上设计文档、四道持续集成门禁与五个混沌演练，并以「契约先行、全员批准」约束所有跨模块改动；评审中发现的隐藏边界（fuzz 测试、WebSocket 合并广播竞态、维克里付款 fixture）随后被正式纳入持续集成（issue #228），把评审纪律沉淀为长期回归门禁。

最后，我们把工程可信度做成了评委可见的界面元素。评委导演模式以六步按钮（末十秒、甲方出价、乙方反超、反狙延时、落锤、证据卡）一键走完拍卖闭环，复用生产组件注入确定性参数，演示当天无需依赖任何网络或种子数据；首页将最热直播场次剧场化为第一屏舞台；每个房间顶部的工程信息条可展开为「连接正常 · 序号 · 漂移 · 出价速率 · 延时次数」，让一致性与实时性这些通常看不见的工程属性，直接呈现在评委眼前。

为压住「百人出价」的轻量基线之外更接近真实直播场景的负载，我们在同一公网拓扑下把出价比例拉高到 4:6——六千名观众加四千名活跃出价者，端到端约每秒两万笔出价的压力。结果是：连接侧 OK 一万、失败为零、峰值并发一万（稳态约 9,874），但有约 1.3%（126 条）连接在拍卖结束前主动关闭并退出；服务端侧在四十倍出价压力下 ack 95 分位仍稳定在 3.5 毫秒、补丁 95 分位 58 毫秒，序号空洞与背压强制关闭均为零，约 99.97% 注定失败的低价出价被网关 fast-reject 提前吃掉而未进入 Lua 裁决。我们的判定是「高活跃 10k SLO / 正确性达标，早退作为诚实边界单独记录」，而**不**将此场景说成「全程零早退」——把这条小尾巴清晰交代出来，正是本作品诚实边界原则的当场兑现。

#### D. 容量边界探测——诚实边界

我们进一步把活跃出价者从一百名拉高到一万名（目标约每秒五万笔出价、总连接约两万），观察系统的崩溃姿态。结果是单网关进程在峰值约一万五千七百七十七（15,777）连接时崩溃并自动重启，但崩溃前后序号空洞始终为零、无客户端被强制关闭，Redis 中的拍卖状态扛过了重启。换言之，进程虽死，正确性始终不破。

我们把这条数据视作亮点而非污点：它证明系统知道自己的容量边界在哪里，且压垮时的姿态是受保护的优雅崩溃与恢复。因此，我们的演示口径不会宣称「单网关稳定支持两万连接、每秒五万笔出价」，这是一处边界发现，而非达标项。后续工作将沿准入控制、多网关扇出与内存上限调优的路线推进。

### 14.2　Prompt 策略与 Agent 流程

拍卖师文本流的系统提示强约束模型的输出边界：限定字数，避开动态禁词，不得承诺超出当前规则的内容，不得编造商品事实（事实只能来自卖家确认过的视觉抽取结果），且必须使用提供的服务端倒计时。用户提示则注入触发类型、确认事实、当前价、近期出价者与剩余时间等上下文。

```text
你是直播间「Lumen 拍卖师」。规则：
- 100–200 字内，避开动态禁词列表
- 不得承诺任何超出当前规则的内容
- 不得编造商品事实（事实只来自卖家确认过的抽取结果）
- 必须使用提供的服务端倒计时

[user]
触发：{trigger}   拍品事实：{confirmed_facts}
当前价：{currentPriceCents}   剩余：{remainingMs} ms   延时次数：{extendCount}
```

视觉事实抽取的提示要求模型仔细看图、输出五到八条不超过三十字的结构化事实，对不确定项标注待确认，并绝不编造图中没有的信息。商品上架到直播的自动化路径可概括为：商家上传图片地址，旁路在五秒硬超时内调用视觉模型（超时即提示手动填写而不阻塞），经后置护栏过滤后返回事实草稿，商家逐项确认后该拍卖方可进入直播。下表给出 AI 旁路的失败兜底矩阵。

| `chaos-redis` | Redis 容器重启 | 重启后以最后序号补齐遗漏事件，事件流间隙为零 |
| `chaos-mysql` | MySQL 容器重启 | 持久化进程自愈重试，无事件丢失 |
| `chaos-ws` | 网关强制关闭全部连接 | 客户端反弹重连，带类型关闭码区分背压与网络两类原因 |
| `chaos-timer` | 定时进程暂停约五秒 | 落锤延后不超过五秒，仅记一条错误日志并自我恢复 |

值得一提的是，戴子涵撰写的对抗测试在协作过程中真实地抓出过两个缺陷：一个是混合模式的排行榜接口意外泄漏当前领头羊的契约缺口，另一个是密封模式落锤脚本的键类型守卫缺口，两者均已在提交中修复。这种「先写反向测试、强制实现对齐契约」的做法，直接服务于评分维度对「独特或前瞻性思考」与「异常兜底」的考察。

### 14.4　用户反馈与内测记录

本作品的内测主要以三人团队的高强度互评形式进行。两周内一百八十余个合并请求全部经过评审，跨模块契约改动严格走全员批准。评审密度上，每个合并请求至少经过一次人工评审与四道持续集成门禁，跨模块契约改动则需全员批准、通常经多轮往复后方才合入。在评审过程中，对抗测试多次先于修复提交，倒逼实现对齐规格。评审与对抗机制不仅抓出契约缺口，也产出二次硬化的样本：指标重置令牌的鉴权从「非常量时间比较」演进到「SHA-256 摘要常量时间比较」（issue #224 经同行评审后由 #230 跟进加固），是「自评 → 同行评 → 加固」的典型；本地一键演示冒烟发现资格预审断言与推荐器实现失配（#225），随即被并入持续集成的模式回归门禁（#226），是「先记规格漂移、再以持续集成守门」的典型。我们尤其坚持一种「诚实面对失败」的文化：当一次公网万级测试因拓扑问题失败时，团队没有掩盖，而是直接以有界声明的方式提交了完整测试报告，并把口径写入演示材料，随后才在改换测试拓扑后取得干净达标的结果。这种把失败记录在案、把边界写清楚的做法，构成了本作品材料完整度与工程可信度的一部分。

### 14.5　AI 输入输出样例

为说明 AI 落地的实际形态，下面给出两个代表性样例（取自演示脚本，演示当天以现场实拍为准），分别展示视觉事实抽取与拍卖师话术生成两条链路，并说明人工确认与后置护栏在其中的位置。

**样例一：视觉事实抽取（VLM）**

输入为一张腕表商品图。视觉模型输出一份结构化事实草稿，每条事实包含字段名、取值、置信度（0 到 1 的浮点数）与是否高风险（布尔值）四个字段。本地开发态的生成器仅返回品类、是否真品等两到三条核心事实，演示当天则以演示脚本预设的事实卡覆盖品牌、型号、成色等更完整的条目；其中「是否真品」一项固定标记为高风险、置信度为零，必须由商家手动确认或填写。商家在后台逐项确认与编辑，全部确认后该拍卖方可由已排期态进入直播态。这一流程体现了我们划定的产品边界：视觉模型只产出待确认草稿，商品描述真实性的最终责任始终落在卖家。

**样例二：拍卖师落锤话术（LLM）**

输入上下文为：触发器为落锤、拍品为某腕表、成交价一万一千八百元、得主显示名为某买家。语言模型据此生成一段不超过八十字的落锤话术，唱出落槌价并恭喜中标者、预告下一场；该话术先经后置护栏校验（无违禁词、无超规则承诺、无编造商品事实，且金额与得主取自服务端事实而非模型臆造），通过后才逐字流式下发到房间。若护栏判定不通过或模型超时，话术降级为预设的短文案兜底——每个触发器各配一句通用兜底文，例如落锤场景下为「落槌成交 · 恭喜得主。」——用户视角下仍能收到一句话术，但不再依赖模型输出；出价路径与状态机不受任何影响。需要与下一种情形区分：此处说的是单次调用失败时的兜底文案，而第 11.5 节所述「AI 离线」指的是整个旁路进程不可用时降级为状态徽标，二者是不同层级的降级。

### 16.2　诚实边界声明

我们认为，把系统的能力边界讲清楚，与把系统的亮点讲清楚同等重要。以下五点是本作品当前的明确边界，均已写入仓库并由全员批准。

- **容量边界**：应用层单房间一万连接已在真公网干净达标；单网关在目标每秒约五万笔出价、峰值约一万五千七百七十七（15,777）连接时进程会崩溃重启，但正确性始终不破。这是边界发现而非达标项，后续进入准入控制与多网关扇出路线。
- **账号鉴权**：尚未接入抖音真实账号的单点登录，当前登录接口为按昵称生成买家令牌的简化模式，仅供赛题演示。
- **支付通道**：尚未接入真实支付，订单的「支付」为模拟支付，并在证据卡上明示。
- **全员付费合规**：仅为演示性虚拟币机制，界面强制显示「虚拟币 · 非真实支付 · 非赌博」，边界写入证据卡契约并经全员批准。本作品并非赌博产品。
- **测试环境与可复现性**：本报告所有性能数字均在火山引擎北京 ECS（4 核 8 GiB）单进程裸二进制下采集；多网关并行扇出、跨地域副本与企业级专线链路未在本作品范围内验证。其中私网内一万并发（Tier-1）有完整的一键复现手册 `docs/runbooks/beijing-tier1-10k-demo.md`，含跳板、压测机配置、令牌分片与运行命令；异地公网压测机打向北京网关弹性 IP 的真公网一万并发（Tier-2）与两万容量边界的拓扑与数据见 `docs/reports/2026-06-07-tier2-public-loadtest-10k-20k.md` 与 issue #233，独立复现手册列为后续工作。

## 十七、评委五分钟核检指引
